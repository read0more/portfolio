에스티컴 / 노스페이스 공식몰 앱 웹뷰 연동

iOS·Android 분기를 브리지 모듈 하나에 모으기

같은 웹 화면이 PC·모바일 브라우저와 iOS·Android 앱의 웹뷰에서 함께 쓰입니다. 화면마다 흩어져 있던 iOS·Android 판별과 응답 해석 코드를 웹의 공통 브리지 모듈 하나로 모았습니다.

화면 코드는 플랫폼을 알 필요가 없습니다

웹에서 앱을 부르는 통로가 iOS는 WKWebView 메시지 핸들러, Android는 앱이 주입한 객체로 서로 다릅니다. 화면이 이 차이를 직접 다루면 기능이 늘 때마다 같은 분기가 복사되고, 호출 방식이 바뀌면 모든 화면을 찾아 고쳐야 합니다. 메시지는 메서드 이름·데이터·콜백 이름의 한 가지 형식으로 두고, 기기 판별과 전송은 모듈 안에서만 하도록 했습니다.

같은 권한을 물어도 두 앱의 응답이 다릅니다

화면이 알고 싶은 것은 허용 여부 하나입니다. 응답 모양의 차이는 모듈에서 해석해 같은 형태로 넘깁니다.

카메라 권한
iOS는 카메라와 사진 접근 상태를 따로 주고, Android는 상태 코드 하나를 줍니다.
위치 권한
두 앱이 쓰는 상태 코드의 범위가 달라, 허용 여부로 바꿔 화면에 전달합니다.
알림 권한
같은 iOS에서도 권한을 요청할 때와 상태를 조회할 때 코드의 의미가 달라 메서드별로 해석합니다.

웹뷰가 브라우저와 달라서 함께 고려한 점

앱 밖에서의 동작
브라우저에는 브리지가 없습니다. 모든 호출에 주소 이동이나 history.back 같은 웹 동작을 함께 두어, 같은 코드가 PC·모바일 웹에서도 동작합니다.
배포된 앱과의 약속
웹은 배포하면 바로 바뀌지만 앱은 사용자가 업데이트해야 바뀝니다. 앱이 이미 쓰는 메서드 이름과 메시지 형식은 그대로 두고 웹의 호출 위치만 옮겼습니다.
화면 사이의 데이터
앱의 페이지 이동은 새 웹뷰를 띄워 sessionStorage가 이어지지 않습니다. 다음 화면에 넘길 값은 쿠키나 서버 세션에 두었고, localStorage는 두 앱의 웹뷰 설정을 읽어 화면 사이에 공유되는 것을 확인했습니다.
끝나지 않는 로딩
네이티브 로딩 표시는 페이지가 바뀔 때만 앱이 닫아 줍니다. 한 화면 안의 비동기 흐름에서는 실패해도 닫히도록 finally에서 직접 닫습니다.

민다 / 호텔 예약 서비스 출시

목록과 지도에 같은 검색 조건을 전달하기

호텔 판매를 시작하며 Next.js 프로젝트의 초기 구성부터 탐색·예약·결제 프론트엔드까지 전담했습니다. 목록과 지도가 같은 호텔을 가리키도록 검색 상태의 기준부터 정했습니다.

URL의 문자열을 조회 조건으로 바꾸는 지점

화면마다 URL 값을 직접 해석하면 가격·성급 필터의 기본값과 잘못된 값의 처리 방식이 달라집니다. 필드별 파서를 훅에 모아 유효한 값만 사용하고, 기본값은 URL에서 생략했습니다. 파싱한 조건을 조회 키로 넘겨 필터와 데이터 요청이 함께 바뀌게 했습니다.

객실을 고르면 검증 대상이 달라집니다

호텔 상세에서 일정이나 인원을 바꾸면 객실 목록을 다시 조회합니다. 결제 화면에 진입할 때는 선택한 객실을 예약할 수 있는지 확인하고, 객실별 인원 정보를 공급사가 요구하는 형태로 구성했습니다.

기존 회원이 결제까지 이어가려면

기존 사이트는 PHP 세션으로, 호텔 API는 액세스 토큰으로 사용자를 식별했습니다. 두 서비스가 함께 운영되는 동안 어느 로그인 상태를 기준으로 삼을지 백엔드 담당자와 정했습니다.

토큰 갱신을 위해 별도의 로그인을 만들지 않았습니다

새 토큰의 발급 근거로 기존 로그인 세션을 사용했습니다. 회원은 다시 로그인하지 않고 호텔 예약을 이어갈 수 있지만, 호텔 화면에서 토큰을 갱신하는 경로는 기존 세션의 유효성에 의존합니다.

기존 PHP 진입점을 전환의 경계로

운영 중인 메인과 서브메인을 개편하기 위해 PHP 위에 React를 올리는 방식을 직접 제안했습니다. 첫 프로젝트 구성부터 빌드 연결, 라우팅과 후속 화면 개발까지 맡았습니다.

화면을 어디서 교체할지 먼저 정했습니다

기존 메인 페이지의 PHP 코드에는 Vite 빌드 결과를 포함시키고, 다른 메인 진입점도 심볼릭 링크로 연결했습니다. 브라우저가 해당 화면에 들어온 뒤에는 React Router가 경로를 해석합니다. 기존 URL을 유지하면서 개편한 화면부터 전환할 수 있었습니다.

데이터 조회의 책임도 함께 이동했습니다

PHP가 데이터베이스에서 직접 읽던 부분은 백엔드 팀이 분리한 API를 React에서 사용하도록 바꿨습니다. 메인·서브메인을 전환하는 동안 다른 PHP 화면은 기존 방식으로 계속 제공했습니다.

Node 12에서 변경 결과를 확인하는 방법

Node 12에서 React 18을 빌드할 수 있었지만 HMR이 동작하지 않았습니다. 빌드 산출물이 바뀌는 순간을 감지해 개발 화면을 새로고침하는 도구를 만들었습니다.

실험한 방법과 남은 제약

처음에는 개발용 Vite 클라이언트와 모듈 진입 파일을 PHP에서 직접 불러왔습니다. Node 12의 ES module 지원을 켜도 CommonJS를 요구하는 의존성과 충돌했습니다. 그래서 소스 모듈 교체를 전제로 하지 않고 빌드 파일이 바뀌는 시점을 감지했습니다.

자동 새로고침이 해결한 범위

수정할 때마다 개발자가 직접 새로고침하던 일은 줄었습니다. 다만 파일을 다시 빌드한 뒤 페이지 전체를 읽는 방식이라 빌드 대기는 남고 화면 상태도 초기화됩니다. 개발 편의를 위한 연결을 운영 코드 경로와 분리한 이유입니다.

번역 문구의 입력 지점을 하나로

같은 번역을 두 번 입력하는 문제를 발견하고, 번역 원본을 하나로 모으자고 먼저 제안했습니다. Google Sheets를 함께 쓰고, 같은 행의 번역을 PHP의 DB와 React의 JSON에 반영하도록 했습니다.

기존 서비스가 문구를 읽는 방법은 유지했습니다

React 대시보드는 react-i18next용 파일을 읽고 PHP 서비스는 DB를 조회하고 있었습니다. 번역자가 두 경로를 따로 관리할 필요가 없도록 입력을 시트로 모으고, 시트를 읽는 쪽에서 각 서비스에 맞는 형태로 변환했습니다.

두 경로에서 맡은 범위

React 쪽은 시트를 파싱해 JSON을 만드는 스크립트와 빌드 연결까지 구현했습니다. PHP 쪽은 같은 시트를 읽어 DB에 적재하는 첫 버전을 작성해 백엔드 개발자에게 인계했습니다.

git-flow 도입과 광고 대시보드 배포 자동화

main 하나에서 개발하던 팀에 git-flow와 통합 테스트를 도입했습니다. PR을 열면 GitHub Actions가 사용자 동작을 테스트하고, 테스트를 통과한 변경 사항을 main에 병합하면 빌드와 배포가 시작됩니다.

PR 검사 결과
npm ci로 의존성을 설치하고 Vitest에서 통합 테스트를 실행합니다. MSW로 API 응답을 재현하고 React Testing Library로 화면을 조작해 결과를 PR에서 확인합니다.
빌드 입력
main을 체크아웃하고 캐시 확인, Node.js 버전 설정, npm ci를 차례로 실행합니다. .env를 설정하고 시트에서 번역 JSON을 생성해 대시보드 빌드에 포함합니다.
배포 순서
GitHub Actions가 빌드 산출물을 S3에 먼저 올립니다. 업로드가 끝나면 CloudFront에 캐시 무효화를 요청해 다음 요청에 새 파일을 제공하도록 합니다.

파이프라인을 구성할 때 고려한 점

검사 생략 범위
필수 검사는 항상 실행하고, 생략 조건은 비용이 큰 단계에만 좁게 둡니다. 새 경로가 추가되면 기본적으로 검사 대상에 포함되도록 합니다.
실패 신호 전달
검사 대상이 비어 통과하거나 결과를 요약하는 과정에서 실패 코드가 사라질 수 있습니다. 실제 실패가 배포를 멈추고 원인이 로그에 남는지 확인합니다.
캐시의 실효성
캐시 적중·미적중 조건을 반복 측정해 복원·저장 비용까지 비교합니다. 실행마다 달라지는 시간보다 절약 폭이 큰지 보고 최적화를 결정합니다.
